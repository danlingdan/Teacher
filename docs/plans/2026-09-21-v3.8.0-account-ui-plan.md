## 1. 目标与范围

v3.8.0 定位为**账号闭环补全 + 界面一致性/观感升级**版本。调研结论（见调研报告）表明：账号体系底座
已完整，缺的是"公网用户能真实走完 注册 → 验证邮箱 → 找回密码 → 资料与设备管理"的生命周期；
UI 底子好，缺的是一致性的工程根因治理与观感档次。本版不重建任何已有系统。

安全与原则边界不动：离线优先、本地学习不依赖网络；密码存储/token/防枚举/审计沿用既有实现；
新增端点全部落限流与审计；AI 与 SQL 安全边界零改动。

### 现状盘点（2026-09-21 调研结论，摘要）

**已有（复用，不动）**：云端 `users`/`user_roles`/双令牌会话/`email_verifications`/`reset_tokens`/
`account_tasks` 全套表结构（`CloudSchemaMigrator` 迁移 1/8）；`/api/v1/auth/*`、`/api/v1/account/*`
（含未接线的 bind-email/verify-email）、`/api/v1/sessions/*` 路由；PBKDF2-310k/常时比较/假哈希防枚举
（`server/Hashes.java`、`CloudAuthenticationStore.java`）；`AuthRateLimiter`+每端点配额+`admin_audit`/
`export_audit`；6 位班级码入班与三层权限强制；客户端 `AuthPage` 三 tab、DPAPI 会话持久化、
`useAccountSecurity`、`HttpCloudApiClient`（含休眠的 `resetPassword`）。

**缺口（本版要补的真实差异点）**：

| --- | --- | --- |
| 1 | 重置邮件依赖不存在的落地页，且只对 `email_verified=1` 发信；自注册用户恒为 0，重置静默失效 | `V111AccountStore.java:162,173` |

### 明确不做（红线延续 + 调研取舍）

- 排行榜、班级排名、监考、行为画像、AI 自动评分——历代红线不变（调研亦支持：排行榜对中后段学生
  是负激励）。
- **第三方 OAuth（微信/Google/Apple）、短信验证码/手机号注册、SSO/LDAP/LTI、青少年模式全套**——
  调研结论：成本与合规负担超出单开发者收益；本软件面向高校、无社交/UGC/内购，不做即是合规最优。
  日 streak 式焦虑设计不做（如做坚持度，用周节奏+安全网）。
- 多教师协作、班级内角色模型变更——v3.3 既定边界继续；本版仅触及"全局 TEACHER 的管理授予通道"
  （ACC-S4，决策点 1），班级内 TEACHER/STUDENT 模型零改动。
- 实时推送、课堂投影、监控类功能——v3.5.0 起既有"另行立项"边界不变。
- 信息架构不推倒重来：侧边栏 + 7 工作区 + 命令面板经行业对照确认正确，仅做呈现精修。
- i18n 正规化（替换 `uiI18n.ts` DOM 替换方案）本版不做，挂入积压清单。

### 决策点（2026-09-21 已确认）

1. **教师角色授予方式：方案 B（教师邀请码）**——管理员生成一次性升级码，教师在客户端兑换
   （ACC-S4 按此实施，见任务清单）。
2. **密码重置/邮箱验证凭证形态：按推荐执行**——邮件发 6 位数字验证码（15 分钟有效、5 次尝试上限），
   客户端手动输码为第一公民；`sqlteacher://` 深链仅为增强项，排在手动输码闭环验证通过之后实施。
3. **UI 改造深度：按推荐执行**——一致性治理（UIX-1/2/4）与档次提升（UIX-3/6/7）两层都随本版交付。
4. **图标方案：按推荐执行**——引入 `lucide-react`，以 `shared/ui` 的 `Icon` 封装收口。
5. **批次数：单版本交付**——全部批次随 v3.8.0 单版本交付（对齐 v3.7.0 先例，2026-09-21 用户决策）。
6. **补充需求（用户 2026-09-21 明确）：账号的邮箱、显示姓名、密码三项均可自助修改**——密码修改走
   既有 `change-password`；显示名走 ACC-S3 `PATCH /api/v1/account/profile`；邮箱换绑走 ACC-S2
   bind-email 验证码流；三者由账号中心（ACC-D3）提供统一入口。

## 2. 任务清单

### A. 云端服务端（ACC-S1…S5）——第一批先行（云端先行部署原则）

- **ACC-S1（P0）SMTP 邮件通道**：新增 `SmtpMailSender`（实现既有 mail sender 契约），配置经环境变量
  `SQLTEACHER_CLOUD_SMTP_HOST/PORT/USERNAME/PASSWORD/FROM/STARTTLS`，未配置时自动降级现有
  `FileMailSender`（行为不变）；连接/认证失败记入服务端日志（脱敏，不含凭据与收件人地址全文），
  邮件发送结果不影响接口的防枚举语义（reset 请求恒 200）。依赖选择：`org.eclipse.angus:angus-mail`
  （jakarta.mail 参考实现，材料性降低自研 SMTP 风险，随计划说明）。
  - 测试：配置解析与降级矩阵用例；密码/凭据不入日志用例。
- **ACC-S2（P0）密码重置与邮箱验证码化闭环**：按决策点 2——
  - `request-password-reset`：账号存在即发 **6 位数字码**，**不再要求 `email_verified=1`**（持邮箱
    收到验证码即持箱凭证，向未验证地址发码无安全增量风险；同时消除"注册后未验证邮箱的用户永久
    无法自助找回"的死角）。不存在的邮箱恒 200 同文案（防枚举保持）。码以 SHA-256 哈希存储（复用
    `reset_tokens` 表，15 分钟过期、`attempts` 上限 5），发码配额沿用既有 reset 限流（3/邮箱/时 +
    10/IP/时）。
  - `reset-password`：接受 `{email, code, newPassword}`（与既有 token 入参 additive 并存，旧字段不删）；
    任何失败（码错/过期/超尝试/账号不存在）统一单一错误码，不区分原因（防枚举）。
  - `bind-email`（含换绑）/`verify-email` 打通为 6 位码流：登录态用户提交新邮箱→向新邮箱发码→验证
    成功后替换 `users.email` 并置 `email_verified=1`（换绑后旧邮箱作为登录标识立即失效；既有会话与
    令牌保持——换绑按资料变更处理，不强制全端登出）；`verify-email` 服务于当前邮箱的补验证。
    发码配额沿用 verify-mail 限流（3/账号/时 + 1/邮箱/天）。
  - 邮件正文更新：验证码 + 有效期 + "非本人操作可忽略"提示（移除指向不存在落地页的链接）。
  - 测试：码哈希存储、过期、尝试上限、错误码矩阵、防枚举语义回归（沿用
    `CloudServerHardeningIntegrationTest` 模式）。
- **ACC-S3（P1）资料与设备（覆盖决策点 6：显示名/邮箱/密码三项可改）**：`PATCH /api/v1/account/profile`
  （displayName ≤80，沿用校验规则；密码修改走既有 `change-password` 不重复建设）；register/login 请求
  additive 增可选 `deviceLabel`（客户端上报，缺省回落"桌面设备"，入库转义与长度截断）；邮箱修改 =

## 3. 风险与边界

- **云端先行**：ACC-S 新端点/新入参要求服务端先于（或同批）客户端部署；旧客户端 + 新服务端必须
  additive 兼容（既有 auth/account/sessions 响应只增不改；`reset-password` 双入参并存期不删旧字段）。
- **邮件通道运维**：SMTP 凭据仅经环境变量注入（不入库、不入 Git、不入日志）；生产部署走 operations
  记录并先验证真实收信；SMTP 不可用时降级文件 outbox，账号闭环在公网退化为"不可自助找回"（与现状
  一致，不倒退）。发送失败不得泄露账号是否存在（防枚举语义保持）。
- **深链协议**：Windows 协议注册涉及安装器（NSIS）与 Tauri deep-link 插件，属打包面变更；设计上
  手动输码为第一公民，深链只是增强，深链故障不阻塞闭环。发布前需重打包验证协议注册。
- **验证码安全**：6 位码必须哈希存储、限时限次、绑定邮箱维度限流（沿用 verify-mail 配额模式）；
  reset/verify 失败文案不泄露账号存在性。
- **schema**：云端零新表（`email_verifications`/`reset_tokens` 已建，复用并 additive 加列如需）；
  若 ACC-S5 随版则 `CloudSchemaMigrator` 加一版迁移。本地无 schema 迁移（ACC-D4 为纯数据更新）。
- **UI 重构风险**：UIX-1/5 的唯一验收是"行为与视觉零变化"（组件测试+视觉巡检 E2E 佐证），
  拆分/替换分小步提交，禁止顺手改样式；图标替换（UIX-3）与 token 收尾（UIX-1）明确分为两批，
  避免一次大改无法定位回归。
- **桥契约**：全部 additive 演进，四处同步一次完成；不改既有方法语义。
- **角色红线**：ACC-S4 仅在决策点 1 获用户批准后实施，且范围严格限于"全局 TEACHER 授予通道"，
  班级内模型与三层权限强制零改动。
