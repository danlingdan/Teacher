## 事件：首启题库迁移中断及修复（已恢复，无数据丢失）

- 首次启动在 `V31ExerciseBankStore.migrateFromLegacySchema` 崩溃
  （`no such table: exercise_bank_blocks`）：迁移先把旧命名表重命名为
  `*_v1` 再回灌新频道表，但回灌目标表在迁移后才由建表逻辑创建，先重命名后回灌
  的顺序在"升级前存在旧版表"的库上必然失败。systemd 自动重启后第二次启动时
  旧命名表已不存在，迁移整体跳过，服务正常启动。
- 后果：生产库中 v3.1/v3.2 时代发布的题库内容（91 个 block、频道版本 19）滞留在
  `exercise_bank_blocks_v1` / `exercise_bank_state_v1`，新频道表为空，
  公网 `bank/channels` 返回空列表。
- 修复（02:03，服务不中断）：先做修复前备份
  `/opt/sqlteacher/backups/cloud-20260912T181500Z-prebankfix.db`
  （SHA-256 `7c155471fcd667b679ad12cbde6387ec7a6a5e03a33a63cebef5f82deabc815b`），
  再在单个事务内按迁移代码的既定映射补齐数据：
  91 个 block 以 `channel='network'` 回灌、`exercise_bank_state` 插入
  `('network', 19, <UTC 时间>)`；随后将两张 `_v1` 表重命名为
  `*_v1_migrated_20260912` 保留观察（未删除）。
- 验证：公网 `bank/channels` 返回 `network`/版本 19，`bank/manifest` 正常列出
  数据集与题目；运行进程 classpath 指向 `Teacher-3.3.3.jar`。
- 跟进：`migrateFromLegacySchema` 的"先改名后回灌"顺序缺陷需代码修复
  （建表先行或失败即整体回滚），避免下一次从旧 schema 升级时复现。
